# 2026-09-23 — Every IPC failure was labelled "unavailable" and replayed over the relay

- **Status:** Resolved
- **Task/context:** `sendCommand` in `src/mcp.ts`, the MCP server's client for the native host's IPC socket. Follow-up to `docs/leanings/2026-09-23-wedged-native-host-swallows-sigterm-and-needs-external-liveness-probe.md`, where an agent reported "the native messaging host died" and the host had not died.
- **Unexpected observation or failure:** `chrome_extract_content` on a `chromewebstore.google.com` tab returned `NATIVE_IPC_UNAVAILABLE: Native Messaging IPC at <socket> is unavailable (Error: The extensions gallery cannot be scripted.)`, while `npm run watchdog` reported the host `alive`. The transport had worked. The host had answered, and the answer was Chrome refusing to script the Web Store. An agent reading that label had every reason to conclude the host was down.
- **Evidence:**
  - `sendIpcCommand` rejected in three different situations (connect failed, client timer fired, host answered `{ success: false }`) and `sendCommand` wrapped all of them in the same `NATIVE_IPC_UNAVAILABLE` text.
  - The regression tests, run against the old code with `CHROME_CONTROLLER_ALLOW_RELAY=1` and a fake relay: a host application error, a client timeout, a host that closed the connection without answering, an unparseable answer, and an `EPIPE` after connecting all resolved successfully with the **relay's** result. Every one of those requests had already reached the host and was replayed over a second transport.
  - The closed-connection case took the full 2000ms timeout before failing over, because there was no `'close'` handler. A host that exits mid-request looked like a wedge.
  - A response whose `☕` was split across two reads came back as `���`: each chunk was decoded with `chunk.toString('utf8')` on its own.
- **Approaches tried:**
  - **Attempt:** Classify failures in `sendCommand` by matching the error text (`'IPC timeout'`, `ECONNREFUSED`, ...).
    - **Outcome:** Did not work
    - **Why:** Rejected on inspection. The host's own application errors contain the same words: `Native Messaging request timed out after 15000ms` is a definitive answer from a healthy host, but text matching would file it as a client timeout. Only the code that saw the event knows which kind it was.
  - **Attempt:** Typed `IpcError` with `kind: 'unavailable' | 'timeout' | 'protocol' | 'rejected'`, set where each event happens in `sendIpcCommand`.
    - **Outcome:** Worked
    - **Why:** The kind records how far the request got. `unavailable` is set only for a socket error before `connect` completed, so the request provably never reached the host.
  - **Attempt:** Keep relay fallback for timeouts, since a wedged host is "unavailable" in practice.
    - **Outcome:** Did not work
    - **Why:** Rejected. After a timeout the host may still be executing a click, fill or tab creation in Chrome. Replaying it over the relay can run it twice. Only a request that never reached the host is safe to retry anywhere.
  - **Attempt:** Treat a socket error after `connect` as `unavailable` when the request write had not finished flushing.
    - **Outcome:** Partial
    - **Why:** Considered, not implemented. It would be more precise: a request whose trailing newline never left the client cannot have been parsed. But it adds state for a rare case, and the conservative `protocol` label costs only a skipped automatic retry. Left conservative.
  - **Attempt:** First version of the fix, checked by an adversarial test critic that ran 29 hand mutations in a scratch copy.
    - **Outcome:** Partial
    - **Why:** It found a regression the fix itself introduced. Answer checks had moved outside the `try`, so a host answer of `null` threw `Cannot read properties of null (reading 'success')` inside the socket handler. That crashes the MCP server, or leaves the call pending forever, because `settled` was already set. `42`/`{}` were reported as host rejections. Now any answer without a boolean `success` is a `protocol` error, checked before settling. The critic also found gaps that let mutations survive: socket leaks after timeout/success, a partial answer followed by close, `injectSecretGuarded` missing from the native-only test, and an `HTTP_PORT` test that passed even if IPC was tried first. Each now has a test.
- **Root cause:** `sendIpcCommand` returned an untyped `Error` for every failure, so `sendCommand` could not tell "could not connect" from "connected and got an answer". It picked the most alarming label and applied the only recovery it had, relay fallback, to all of them.
- **Resolution:**
  - `sendIpcCommand` rejects only with `IpcError`. `unavailable` is set for socket errors before connect. `timeout` is set when the client timer fires. `protocol` covers a socket error after connect, a close without a newline-terminated answer, or an unparseable answer. `rejected` means the host answered `success: false`.
  - `sendCommand` falls back to the relay only for `unavailable`, and never for native-only actions. `NATIVE_IPC_UNAVAILABLE` keeps its text. Timeouts become `NATIVE_IPC_TIMEOUT` and point at `npm run watchdog`, whose `hostPing` is answered by the host without Chrome and so separates a wedged host from a slow Chrome. Broken connections become `NATIVE_IPC_PROTOCOL_ERROR`. Host answers pass through verbatim.
  - Added a `'close'` handler so a host that exits mid-request fails fast, and switched the socket to `setEncoding('utf8')` for streaming decode.
- **Verification:** The new tests were run against the pre-fix `src/mcp.ts`. The six behavior tests failed for the reason each names: application error, timeout, closed connection, unparseable answer, post-connect EPIPE, and split UTF-8. The first five resolved with the relay's result instead of rejecting. The transport-failure and native-only tests failed only on the new `kind` field; their messages and no-relay behavior were already right. The fallback-on-unavailable test passed before and after, so the existing fallback is preserved. Hand mutation: classifying every socket error as `unavailable` is caught by the post-connect EPIPE test. After the critic's findings: the new `null`-answer test hung the suite against the intermediate code and passes now. `npm test` (207 pass), `npm run typecheck`, `npm run lint` pass.
- **Prevention/follow-up:** The tests run a fake host on a temp socket via `CHROME_CONTROLLER_SOCKET`, plus a relay reachable only through a private discovery file. `HTTP_PORT` stays unset, so IPC is really attempted first. The old "falls back to HTTP relay" test set `HTTP_PORT`, which skips IPC entirely, so it never exercised the fallback. It is renamed to say what it covers. Remaining: `src/index.ts` (Pi extension) has the same timeout mislabel, the same relay replay, and the same chunk decoding. Also, ordinary MCP commands give up after 10s while the host waits 15s for Chrome, so a slow Chrome still yields the ambiguous client timeout instead of the host's definitive answer.
- **Reusable learning:** Classify a failure where it happens, by how far the request got, not by its message text. Retry over another transport only when the request provably never reached the first one. Once a peer has received a command, any retry can duplicate it. An error label is itself operator guidance, and a wrong one sends people and agents to fix a healthy component.
